# 역설계 완성도 감사 및 보완 계획

**기준**: "이 문서만으로 33m2 / Airbnb와 거의 동일한 서비스를 구현할 수 있는가?"
**판정**: ❌ **불가.** 종합 완성도 약 30%.

---

## 1. 산출물별 완성도

### 1.1 데이터 모델 — 약 17%

| 상태 | 엔티티 |
|---|---|
| ✅ 문서화됨 (4) | `Room`(56필드) · `Host` · `SimpleReviewTag` · `RoomListItem` |
| ❌ 누락 (~20) | `User/Account` · `Contract` · `ContractEvent`(타임라인) · `Payment` · `Settlement` · `SettlementLine` · `ChatThread` · `ChatMessage` · `AutoMessage` · `Notification` · `NotificationSetting` · `Review`(자유 텍스트) · `ReviewReply` · `Favorite` · `RecentRoom` · `RoomSchedule` · `RoomPicture` · `LongTermDiscount` · `EarlyCheckinDiscount` · `RefundTerm` · `Campaign/Article` · `Notice` · `FAQ` · `Inquiry` |
| ❌ Airbnb | 구조화된 엔티티 **사실상 0개** (섹션 ID 목록만 있음) |

**치명적 공백**: 계약·결제·정산은 이 서비스의 **핵심 도메인**인데 필드 하나도 확정되지 않았습니다.

### 1.2 API 명세 — 약 5%

- 33m2: **4개** 엔드포인트 (`map/rooms`, `map/markers`, `rooms/{rid}/schedules`, `contracts/last-active`)
- Airbnb: GraphQL 오퍼레이션 **3개**
- ❌ 에러 코드 체계 — 성공 코드 `SCSS_001` 하나만 앎. 실패 응답을 한 번도 못 봄
- ❌ 인증 — Firebase 사용 사실만 앎. 토큰 형식·갱신·헤더 규약 미확인
- ❌ 쓰기 계열 전무 — 계약 생성/승인/취소, 메시지 발송, 찜, 리뷰, 매물 CRUD
- ❌ 검색 필터 실제 파라미터명 미확인 (UI만 봄)
- ❌ 정렬 옵션, 레이트리밋

### 1.3 화면 인벤토리 — 약 35%

| 축 | 상태 |
|---|---|
| 라우트 목록 | 🟡 나열은 했으나 33m2 게스트 17개 중 **7개만 실제 탐색** |
| 데스크톱 레이아웃 | 🟡 주요 화면만 |
| **모바일/반응형** | ❌ **0%** — 968~1148px 데스크톱만 관찰. 두 서비스 모두 모바일 트래픽이 주력 |
| **디자인 토큰** | ❌ **0%** — 색상·타이포 스케일·간격·라운드·그림자·모션 전무 |
| **컴포넌트 스펙** | ❌ 버튼/칩/카드/입력 변형과 상태(hover/focus/disabled/error) 없음 |
| 상태 변형 | 🟡 빈 상태 일부만. 로딩·에러·부분실패 없음 |
| 아이콘 | ❌ |

> 색·폰트·간격 없이는 "거의 동일한 서비스"가 성립하지 않습니다.

### 1.4 유저 플로우 — 약 40%

| 상태 | 플로우 |
|---|---|
| ✅ | 탐색→계약요청, 계약 상태 머신, 요금 계산, 가용일 판정 |
| ❌ | **회원가입 · 로그인 · 본인인증 · 비밀번호 재설정 · 로그아웃 · 탈퇴** |
| ❌ | 리뷰 작성 · 리뷰 답글 |
| ❌ | 계약 취소 실행 · 환불 처리 |
| ❌ | 기간 연장 신청/승인 |
| ❌ | 퇴실 점검 · 보증금 반환/차감 |
| ❌ | 매물 신규 등록(수정 위저드와 다름 — 주소 입력 단계 존재) |
| ❌ | 1:1 문의 · 신고 |
| ❌ | Airbnb: 예약 확정 이후 전 과정 |

### 1.5 권한 모델 — 약 55%

뼈대와 핵심 규칙(`ONLY_AFTER_CONTRACT_CONFIRMED`)은 확보. 다만 `❓` 비중이 높고, **비로그인 상태의 33m2 접근 범위를 한 번도 테스트하지 않았습니다.**

---

## 2. 왜 이렇게 됐나 — 놓친 기회

1. **RSC 추출 기법을 매물 상세에만 적용했다.**
   `self.__next_f` 파싱으로 Room 56필드를 얻었으면서, 계약/정산/채팅/호스트 페이지에는 쓰지 않음.
   → 이 페이지들에도 서버가 직렬화한 엔티티가 그대로 들어 있음. **가장 큰 미수확.**

2. **i18n 사전을 `common` 하나만 봤다.**
   전체 네임스페이스를 뽑으면 **모든 UI 문구 · 검증 메시지 · 에러 메시지 · enum 표시명**이 한 번에 나옴.

3. **모바일을 아예 안 봤다.**

4. **디자인 토큰 추출을 시도조차 안 했다.** `getComputedStyle`로 쉽게 뽑을 수 있음.

5. **에러를 한 번도 유발하지 않았다.** 잘못된 파라미터로 API를 호출하면 에러 코드 체계가 드러남.

## 3. 보완 계획

우선순위 = (구현 필수도 × 추출 용이성).

### Phase 1 — 33m2 서버 데이터 전면 추출 【최우선·고수확】

| 작업 | 기법 | 산출 |
|---|---|---|
| P1-1 | 전체 i18n 네임스페이스 덤프 | 모든 UI 문구·검증/에러 메시지·enum 표시명 |
| P1-2 | 계약 목록/상세 RSC 페이로드 파싱 | `Contract`, `ContractEvent` 엔티티 |
| P1-3 | 정산 목록/상세 RSC 파싱 | `Settlement`, `SettlementLine` |
| P1-4 | 채팅 RSC + 소켓/폴링 관찰 | `ChatThread`, `ChatMessage` |
| P1-5 | 호스트 방관리/일정 RSC 파싱 | `RoomSchedule`, 매물 관리 상태 |
| P1-6 | 매물 상세 `pictures[]`, `reviewList[]` 완전 전개 | `RoomPicture`, `Review` |
| P1-7 | 알림 설정 RSC 파싱 | `NotificationSetting` |

### Phase 2 — API 표면 확장

| 작업 | 기법 |
|---|---|
| P2-1 | 필터·정렬·페이지네이션을 UI로 조작하며 XHR 캡처 → 실제 파라미터명 |
| P2-2 | 잘못된 파라미터/존재하지 않는 ID로 호출 → **에러 코드 체계** |
| P2-3 | 인증 헤더 규약 관찰 (Firebase ID 토큰 전달 방식) |
| P2-4 | 위저드 각 단계 저장 시 발생하는 **쓰기 API** 캡처 (실제 저장 없이 관찰 가능한 범위) |
| P2-5 | Airbnb GraphQL 오퍼레이션 인벤토리 — 번들에서 persisted query 이름 수집 |

### Phase 3 — 디자인 시스템 추출

| 작업 | 기법 |
|---|---|
| P3-1 | CSS 커스텀 프로퍼티 + `getComputedStyle` 스캔 → 색상 팔레트 |
| P3-2 | 타이포 스케일 (font-family/size/weight/line-height 조합 빈도 집계) |
| P3-3 | 간격·라운드·그림자 토큰 |
| P3-4 | 버튼/칩/입력/카드 변형별 상태 스펙 |
| P3-5 | 브레이크포인트 추출 (미디어 쿼리 파싱) |

### Phase 4 — 모바일/반응형

| 작업 |
|---|
| P4-1 | 390×844로 33m2 게스트 핵심 화면 재순회 |
| P4-2 | 33m2 호스트 핵심 화면 |
| P4-3 | Airbnb 검색/PDP/체크아웃 |
| P4-4 | 데스크톱↔모바일 레이아웃 차이 및 모바일 전용 UI(바텀시트·탭바) 기록 |

### Phase 5 — 미탐색 플로우

| 작업 | 비고 |
|---|---|
| P5-1 | 33m2 비로그인 접근 범위 테스트 | 세션 유지하며 별도 확인 방법 필요 |
| P5-2 | 로그인/회원가입 화면 구조 | 제출하지 않고 폼 구조만 |
| P5-3 | 매물 신규 등록 위저드 (수정과 차이) | |
| P5-4 | 리뷰 작성 폼 | 작성 가능한 계약 없으면 UI만 |
| P5-5 | 33m2 미탐색 라우트 일괄 순회 | 찜/최근본방/FAQ/공지/이벤트/고객센터 |
| P5-6 | 검증 에러 유발 (빈 폼 제출 시도) | 실제 저장 유발 안 되는 범위에서만 |

### Phase 6 — 문서 재구성

- 엔티티별 필드 표(타입·널러블·제약·기본값) 정규화
- 상태 머신 다이어그램(mermaid)
- API를 OpenAPI 3.1 YAML 사이드카로 병행 출력
- 디자인 토큰을 JSON 사이드카로 출력
- 화면별 컴포넌트 트리

## 4. 한계로 남을 것 (원리상 추출 불가)

정직하게 미리 표시합니다.

| 항목 | 사유 | 대응 |
|---|---|---|
| 서버 내부 로직 | 관찰 불가 | 입출력으로 역산 |
| DB 실제 스키마 | 〃 | API 응답에서 추론 |
| 랭킹/추천 알고리즘 | 〃 | 노출 신호만 기록 |
| 배치/스케줄러 | 〃 | 관찰된 시점 규칙만 |
| 관리자(어드민) | 접근 불가 | 필요 기능 추론 |
| 결제 PG 연동 상세 | 실결제 불가 | 화면·상태만 |
| Airbnb 호스트 요금/수수료 | 실물 사진 5장 필요 | 사용자 협조 시 가능 |
| 33m2 퇴실점검/보증금반환 | 해당 상태 계약 없음 | 실계약 발생 시에만 |

## 5. 목표 완성도

| 산출물 | 현재 | Phase 1~6 후 목표 |
|---|---|---|
| 데이터 모델 | 17% | **85%** |
| API 명세 | 5% | **70%** |
| 화면 인벤토리 | 35% | **85%** |
| 유저 플로우 | 40% | **80%** |
| 권한 모델 | 55% | **85%** |
| 디자인 시스템 | 0% | **75%** |
| **종합** | **30%** | **80%** |

80%면 "문서만 보고 구현 착수 → 세부는 스크린샷 대조로 보정" 수준입니다.
100%는 원리상 불가능하며(서버 내부 로직), 목표로 삼지 않습니다.
