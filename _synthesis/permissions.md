관찰된 접근 제어 규칙. `✅` = 확인 · `❓` = 추정

## PERM-01 주체(Principal) 모델

### 33m2 — 단일 계정 · 이중 역할 ✅
```
User (uid)
 ├─ 임차인(tenant) 모드   /guest/*
 └─ 임대인(landlord) 모드 /host/*
```
- **동일 계정**이 두 모드를 전환 (헤더 "임대인 모드로 전환" / "임차인 모드로 전환")
- 계정 정보 화면이 모드별로 다름: `/guest/my/account`(역할 라벨 "임차인") vs `/host/my/account`("임대인")
- 임대인 모드에만 존재하는 필드: **임대인 소개(30자)**, **정산 계좌**, **수수료 영수증(전자세금계산서) 설정**
- 인증: **Firebase Authentication**

### Airbnb — 단일 계정 · 역할 + 위임 ✅
```
User
 ├─ 게스트         /  · /trips · /guest/inbox · /wishlists
 ├─ 호스트         /hosting/*
 ├─ 공동 호스트(co-host)      ← 타 호스트 리스팅에 대한 위임 권한
 └─ 예약 대행 권한 [NEW]       ← 타인 대신 예약하는 권한
```
- 계정 설정에 `예약 대행 권한`, `출장(비즈니스 트래블)` 축 존재
- **본인 인증(Identity verification)** 상태를 별도 보유

> 💡 새 서비스: 33m2식 단일 계정 이중 역할이 국내 현실(임대인이 곧 임차인인 경우 많음)에 적합.
> 단, Airbnb의 **공동 호스트** 개념은 위탁관리 업체 대응에 필요할 수 있음.

## PERM-02 리소스별 접근 매트릭스 (33m2)

`O` 허용 · `X` 불가 · `△` 조건부

| 리소스 | 비로그인 | 임차인(타인) | 임차인(계약 당사자) | 임대인(소유자) |
|---|---|---|---|---|
| 매물 목록/지도 | O ❓ | O | O | O |
| 매물 상세 (기본 정보) | O ❓ | O | O | O |
| 매물 **상세 주소(동/호수)** | X | **X** | **O** ✅ | O |
| 상대방 **연락처(전화번호)** | X | **X** | **O** ✅ | O(임차인 연락처) |
| 찜 (`like`) | X ❓ | O | O | — |
| 계약 요청 생성 | X | O | — | — |
| 계약 승인/거절 | X | X | X | **O** |
| 계약 상세 조회 | X | X | O | O |
| 채팅 | X | △(문의) | O | O |
| 후기 작성 | X | X | **△ 이용완료 후** | ❓(답글 가능 — FAQ 언급) |
| 매물 등록/수정/삭제 | X | X | X | **O (본인 매물만)** |
| 일정(캘린더) 변경 | X | X | X | **O** |
| 정산 내역 | X | X | X | **O** |
| 자동 메시지 설정 | X | X | X | **O** |

### 핵심 규칙 ★
1. **`ONLY_AFTER_CONTRACT_CONFIRMED`** ✅
   계약 확정 전: 지번/도로명까지만, 연락처 비공개
   계약 확정 후: **상세 주소(층·호수) + 양측 전화번호 공개**
   근거: 등록 위저드 "상세 주소는 계약이 확정된 후 공개됩니다", 계약 상세 화면에 양측 연락처 노출
2. **개인화 필드는 조회자 컨텍스트에 종속** — 목록/상세의 `like`, `cid`(조회자의 해당 매물 계약)
3. **소유권 스코프** — 임대인은 본인 매물/계약/정산만
4. **역할 전환은 권한 상승이 아님** — 같은 uid, 리소스 소유권으로 분리

> ⚠️ **33m2와 결정적 차이**: Airbnb는 **비로그인으로도 검색·상세·요금·리뷰 전체 열람 가능**.
> 33m2는 관찰 시점에 이미 로그인 상태였으나, `/v1/**use-auth**/…` 네임스페이스와 `/v1/**no-auth**/…` 규약의 존재로 보아 비인증 접근 경로가 설계되어 있음 ❓.
> 🔵 **새 서비스 권장**: SEO·유입을 위해 **비로그인 열람 전면 허용**, 찜·요청·채팅만 로그인 게이트.

## PERM-04 상태 기반 권한 (계약 상태 머신 연동) — 33m2 ✅

| 계약 상태 | 임차인 가능 | 임대인 가능 |
|---|---|---|
| `계약대기` (요청됨) | 취소 ❓ | **승인 / 거절** (24h 내) |
| `입주대기` (승인+결제) | 취소(위약금) | 취소(위약금 지급) |
| `거주중` | 채팅 · 연장 신청 ❓ | 채팅 · **전화하기** |
| `퇴실중` | — | **퇴실 점검** |
| `계약종료` | **후기 작성** | 후기 답글 ❓ |
| `취소` / `결제취소` | 조회만 | 조회만 |

**자동 전이 규칙** ✅
- 승인 후 미결제 → `취소` ("임차인이 결제하지 않아 취소되었습니다")
- 동일 기간 타 계약 결제 완료 → 나머지 `취소` ("다른 임차인의 결제로 취소되었습니다")
- 승인 24시간 초과 → 만료 ❓

**UI에서 관찰된 조건부 액션**
- `[전화하기]` 버튼은 **거주중** 카드에만 노출 ✅ (계약종료 카드에는 `[채팅하기]`만)
- `[입주•퇴실 일정]` 링크는 결제 완료된 계약에만 노출 ✅

## PERM-07 계정 상태 / 제재 ✅

33m2 i18n 사전에서 발견:
- `dialog.title`: **"규정 위반으로 이용이 중지되었습니다"** → 계정 정지 상태 존재
- `error.restricted`: **"사용중이신 기기 또는 네트워크에서 비정상적인 트래픽이 감지되어 접속이 제한되었습니다"** → 레이트리밋/봇 방어 (IP·디바이스 단위)
- `error.not_found`: 404 처리

> 새 서비스도 `SUSPENDED`(규정 위반), `RATE_LIMITED`(비정상 트래픽) 상태를 초기부터 모델에 포함할 것.

## PERM-08 새 서비스 권장 권한 모델 (초안)

```
Principal
  User { id, roles: Set<GUEST|HOST|ADMIN>, identityVerified, status: ACTIVE|SUSPENDED }
  Delegation { grantorUserId, granteeUserId, scope: CO_HOST|BOOKING_AGENT, listingIds[] }

Resource ownership
  Listing.hostUserId          → HOST 권한의 스코프 기준
  Contract.{guestUserId, hostUserId}  → 양 당사자만 접근
  Settlement.hostUserId
  Thread.participantUserIds

Field-level visibility  (핵심)
  Listing.addressDetail   : PUBLIC_AFTER = CONTRACT_CONFIRMED
  User.phoneNumber        : PUBLIC_AFTER = CONTRACT_CONFIRMED (상대방에게만)
  Listing.exactCoordinate : 계약 전 지오퍼징(±100~200m), 확정 후 정확 좌표

Anonymous access
  검색 · 리스팅 상세 · 요금 계산 · 리뷰 열람  → 허용 (SEO)
  찜 · 계약 요청 · 채팅 · 여행/계약 목록      → 로그인 필요
```
